### 2. Row-level rejection + NDJSON — `src/silver/registers/loader.py`

Two hard requirements from Steve, both delivered: **row-level, not file-level**
rejection, and **NDJSON alongside CSV**.

- New table `rejected_row` (tenant `012`) — one row per rejection, FK'd to
  `ingest_batch`, `column_name` nullable. Kept **separate** from
  `quarantined_artefact`: a row rejection means the file succeeded (a batch
  exists); a quarantine means it didn't (no batch at all). Collapsing them
  would force a nullable `batch_id` and lose the FK.
- `_parse_row` is the **one** validation rule; `parse_register_csv` and
  `parse_register_ndjson` each do only the format-specific job of producing
  `cells: dict[str, str | None]` + a line number. A bug fixed in `_parse_row`
  is fixed for both formats by construction — this is what "modular" meant in
  the brief.
- FATAL (bad encoding, missing required column, zero rows) still quarantines
  the whole artefact, unchanged. PER-ROW is everything else: the batch is
  created from what's valid, `rejected_row` carries the rest.

Re-check: `pytest tests/conformance/test_registers.py -k ndjson -q`,
`pytest tests/conformance/test_registers.py::test_a_partially_bad_file_promotes_the_good_rows_and_records_the_rest -q`

### 3. Bronze intake gate — `src/bronze/scan.py`, `src/bronze/filecheck.py`

Gate order, ahead of the existing `hash -> dedup -> PUT -> INSERT`:

```
file-check -> hash -> dedup check -> virus scan -> PUT object -> INSERT ledger row
```

Virus scanning is a `Protocol` (`VirusScanPort`), **per Steve's explicit

- `ClamAVScanner` — real, working adapter over clamd's `INSTREAM` wire

**`docker-compose.yml` was NOT touched** — no live `clamd` container was

Wiring a real ClamAV service into local dev is unstarted and unrequested —
flag it if you want it.

### 4. Customer-facing outcome query — `SilverReader.artefact_outcome`

The feature that was the original motivation for this whole thread of work:
"did my upload succeed, and if not, why." One method, `SilverReader
.artefact_outcome(ctx, bronze_ingest_id)`, returns an `ArtefactOutcome` with
four states checked in pipeline order:

| Status | Meaning |
|---|---|
| `PENDING` | Received into Bronze, not yet promoted or quarantined |
| `QUARANTINED` | File-level failure, no batch exists — `quarantine_reason` explains why |
| `ACCEPTED` | Every row promoted, `rejected_count == 0` |
| `PARTIAL` | Batch exists, some rows didn't land — `rejections: tuple[RowRejectionDetail, ...]` |

New migration `013_v1_outcome_views.sql` adds `v1_rejected_row` and
`v1_quarantined_artefact` (recon had no read contract for either table before
this) plus an index on `rejected_row.bronze_ingest_id`, since the query starts
from the artefact a customer uploaded, not the batch.

**One subtlety worth knowing if you touch this:** `ArtefactOutcome.row_count`
is deliberately `accepted_count + rejected_count`, NOT
`ingest_batch.row_count` — that column already means "rows accepted into the
batch" (that's what `RegisterLoader` writes there). A first draft of this
method conflated the two and two tests caught it immediately. Read the
field's docstring in `src/reader/silver_reader.py` before changing this.

Re-check: `pytest tests/conformance/test_outcome.py tests/handoff/test_outcome_gate.py -q`

### A real architectural finding, not just a caught bug

Attempting to mark `PURCHASE_REGISTER` as "retired from archetype 1" by
setting `document_type.archetype = NULL` in the registry hit
`document_type_scope_ck` (shared migration `003`): **`archetype IS NOT NULL`
is mandatory whenever `in_scope`**. So archetype cannot be used as a "this
type moved off the old path" signal — a shared migration was reverted
mid-session and the guard was moved to application code instead
(`promote.py`'s `_RETIRED_ARCHETYPE_1_TYPES` frozenset). If a future session
needs to retire another archetype-1 type, use this pattern, not a registry
flip.

## The one thing not to undo

A declarative spec can drift from the DDL it describes — rename a column in a
migration and the spec still names the old one, with **nothing failing until a
real client file arrives**. That is a worse failure than the duplication it
avoids, so it is not merely accepted:

`tests/conformance/test_register_specs.py` reads `information_schema` and
`pg_index` on a live tenant schema and asserts, per type: the column set, the
column **order** (`row_hash` is computed in spec order, so a reorder silently
changes every hash), the required flags, the type kinds, the period column, and
the unique index's columns.

**The table is the source of truth; the spec is a projection of it.** All 141 of
those assertions passed on their first run against the live schema. Do not
"simplify" that gate away — it is the entire reason the spec approach is safe.

Re-check: `pytest tests/conformance/test_register_specs.py -q`

### The third one found a real defect — read this before touching the indexes

Three natural keys include `supplier_gstin`, which is **nullable** because an
unregistered supplier is legitimate: `purchase_register`,
`creditor_ageing_report`, `common_input_service_invoice`.

**A unique index treats two NULLs as distinct.** So the partial unique index does
*not* forbid two live rows for the same `(entity, gstin, NULL, invoice_no)`. It
only looks like it does.

- The **loader is correct**: it matches nullable key columns with
  `IS NOT DISTINCT FROM`, so a resubmitted RCM purchase supersedes rather than
  duplicating.
- The **index is not**: two concurrent loads can still both insert, and nothing
  stops them.

Open in `TODO.md` under "A natural key containing a NULLable column does not
enforce itself" — a `NULLS NOT DISTINCT` migration. **Cheap now, while the tables
are empty; after real data it needs a duplicate sweep first.**

## Two decisions made this session, both worth knowing

**1. Content-keyed registers cannot supersede, and that is visible in a test.**
Eleven of the 23 carry no document identifier (a bank row, a cost allocation, a
trial-balance line), so they are keyed on `(entity_id, gstin, period, row_hash)` —
the reference schema's key. A correction therefore lands **beside** the original
rather than replacing it. That is a limitation of those registers, not of the
schema, and `test_a_changed_row_supersedes_under_a_natural_key_and_appends_under_a_content_key`
asserts both halves. Anyone who "fixes" it by inventing a natural key for a bank
statement fails there, which is the point.

**2. Identical rows within one file are collapsed and COUNTED, not rejected.**
Two byte-identical ECS debits on the same day are plausibly two real payments; on
a trial balance they are an export bug. A content-keyed table cannot tell them
apart. So one is kept and the drop is surfaced as
`RegisterOutcome.collapsed_duplicates` — the alternative was failing the file or
losing the row in silence.

### Then: the ingestion surface — discussed 2026-08-07, agreed in principle, not built

There is **no HTTP API, no worker, and nothing watching object storage**. Every
loader is a library a caller must invoke; `src/cli.py` has only `migrate`,
`provision`, `drift`.

Re-check: `grep -rl "fastapi\|graphql\|strawberry\|uvicorn" --include=*.py --include=*.toml .`
(returns nothing as of this session).

Agreed shape:

| Layer | Surface | Why |
|---|---|---|
| Upload / register artefact | REST | One call per file, wraps `BronzeIngestionService` |
| Trigger + status | REST | Coarse, idempotent |
| **Bronze→Silver load** | **no API** — worker calls the loader directly | See below |
| Read | GraphQL over the `v1_` views, `reader` role | |

**Why the upsert must NOT go behind an API** — this is the part to re-argue if
someone proposes otherwise:

1. A register is 50k–500k rows. Per-row HTTP is a throughput problem; batch HTTP
   reinvents `COPY` badly.
2. Isolation is `SET LOCAL ROLE` **inside one transaction** (invariant 2). An HTTP
   hop either breaks the transaction boundary or forces the API to hold a
   transaction open across the network.
3. The bitemporal supersede is an UPDATE + INSERT that must be atomic with the
   batch manifest row.

**Tenant routing is already solved structurally** — `TenantContext` +
`TenantScopedPool`. What is missing is only resolution at the edge: auth token →
tenant slug → `SET LOCAL ROLE`, once per request. **Never a parameter a client can
pass.** Same mechanism for ingest and GraphQL; GraphQL gets the reader role and
can only see `v1_` views, so a routing bug is a failed query rather than a leak.

Also unsettled and worth raising early: **JSON and Excel are not parsed.** Every
loader takes CSV bytes. Steve's stated intake is "JSON / Excel to MinIO", so an
adapter layer is real work that nobody has scoped.

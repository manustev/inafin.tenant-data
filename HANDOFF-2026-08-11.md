## 1. Ingestion-flow gap analysis (discussion only, no code)

Steve described a proposed Portal-upload flow and a status state machine and
asked for a gap analysis against the current implementation before any
change. Findings, most important first:

### The proposed status state machine conflicts with an existing invariant

Proposed: `RECEIVED → BRONZE_STORED → BRONZE_VALIDATING → BRONZE_VALIDATED →
QUEUED → PROCESSING → COMPLETED` (+ `BRONZE_VALIDATION_FAILED`,
`PROCESSING_FAILED`, `PARTIAL_SUCCESS`, `FAILED`), implemented as a single
mutable status field that advances in place.

`artefact_ledger` **used to have** exactly this shape — a `status` column,
seeded vocabulary `RECEIVED`/`PARSED`/`PROMOTED`/`QUARANTINED`/`REJECTED` in
`platform_ref.universal_master` — and it was **deliberately removed** in
tenant migration `005_bronze_insert_only.sql`. That migration's own header
explains why: status, `promoted_batch_id` and `error_detail` were
"conclusions we reached LATER about a file, stored on the record of what the
customer sent," which made Bronze mutable and gave it an opinion. This is
`CLAUDE.md` invariant 6 (Bronze records fact, Silver records judgement).

Today "status" is not stored at all — it's **computed on read** by
`SilverReader.artefact_outcome`, from three independent signals: does a
`quarantined_artefact` row exist, does an `ingest_batch` row exist, how many
`rejected_row` rows exist. Implementing the proposed state machine literally
(an UPDATE-in-place column) would directly undo migration 005's decision.
**This needs a conversation with Steve before any schema work, not a patch.**
The most likely resolution: the 11 proposed names become the *presentation*
of the existing computed outcome, not a new stored column — but that's a
decision, not yet made.

### Other confirmed gaps (none require re-litigating an invariant)

1. **No Bronze→Silver dispatcher.** Unchanged from `TODO.md` priority 2 —
   `POST /artefacts/{id}/trigger` records intent only. This is the actual
   blocker for "QUEUED → PROCESSING" to mean anything in the proposed flow.
2. **Two IDs, not one.** `ingest_id` (Bronze, minted at upload) and
   `batch_id` (Silver, minted only at successful promotion — a quarantined
   file never gets one). The proposed flow's single "injection_id" concept
   needs to be reconciled with this, or the Portal needs to know which ID
   means what at which stage.
3. **Multi-file upload isn't supported.** `POST /artefacts` takes exactly one
   `UploadFile`; the proposed flow says "one or more files."
4. **Registry-driven validation isn't at intake.** `document_type` is
   accepted and stored as declared, but not checked against
   `platform_ref.document_type` (known/in-scope) until whatever loader
   eventually runs — which today is never, automatically. "Supported
   document/data category" as an upload-time validation doesn't exist yet.
5. Everything else in the seven-item Upload API requirement list Steve gave
   (tenant auth, file type, file size, duplicate detection, ack-then-poll)
   **is already built** and matches.

No action taken — this was requested and delivered as analysis only.

## 2. Archetype 3 extraction — the blocker is lifted

`TODO.md`'s Archetype 3 item has said since 2026-08-06: *"no LUT or EPCG
sample exists anywhere in the workspace... a tier-1 parser written against a
guessed layout is fiction that passes its own tests."* `CLAUDE.md`'s "Why
extraction adapters are not next" said the same. **Steve has now placed real
sample documents in `reference/A1-A7Documents/`** — 50 PDFs covering A2.01
through A7.05 (all of A2–A7, not just LUT/EPCG).

### What was checked this session (inspection only, no adapter code written)

Installed `pypdf` (`uv pip install pypdf`, dev-only, not yet added to
`pyproject.toml` — it was a throwaway inspection, not a dependency
decision) and extracted text from all 50 files. **Every one has a real,
native text layer** — none are scanned images. They're clean,
machine-generated, consistent `Label: Value` layouts, e.g.:

```
LUT ARN: AD2704240123456
GSTIN: 27AABCM4521F1Z5
Financial Year: 2024-25
...
EPCG Licence No.: 0530012876
CIF Value of Import Permitted: 4,80,00,000₹
Duty Saved: 86,40,000...₹
Export Obligation (EO): 6 times the duty saved, i.e., 5,18,40,000...₹
```

Every file is also explicitly labelled `SAMPLE / SPECIMEN DOCUMENT — FOR
PIPELINE TESTING ONLY`, fictitious entity ("Meridian FabTech Industries Pvt
Ltd") reused across the set — worth knowing so nobody mistakes this for a
real client's data later.

**This changes, but does not remove, the earlier caution.** The asymmetry
argument in `CLAUDE.md` ("mock an ERP CSV, never mock a government PDF's
layout") was about *us* guessing a layout with no ground truth. These
specimens are still synthetic — Steve generated them, we don't know how
faithfully they mirror a real DGFT/GST-portal PDF's exact layout — but they
are a real, shared, versioned fixture now, which is the thing that was
actually missing. Building a tier-1 parser against them is legitimate in the
same way `gen_mock_erp.py`'s ERP fixtures are: the risk is "does this match
reality," not "does this fixture even exist."

### Design discussion: PDF text reader → PaddleOCR fallback

Steve proposed a two-stage text-extraction tier ahead of field parsing: try
the native PDF text layer first, fall back to PaddleOCR when there isn't one.
Evaluated against the extraction design already agreed 2026-08-06
(`TODO.md`), which is **not being re-derived, only extended**:

- The existing design's three outcomes (`Extracted`, `Partial(missing,
  failed)`, `NoTextLayer`) already name `NoTextLayer` as "the scanned-PDF
  case, detectable before parsing." The OCR fallback slots in as a **new step
  0** ahead of the tier-1 deterministic field parser: extract native text →
  if absent/near-empty → OCR → then the same field parser runs on whichever
  text resulted, native or OCR'd.
- **Open question, not yet decided:** does `NoTextLayer` now mean "no text
  layer AND OCR also failed," or does OCR success just become a silent new
  source of truth? This isn't cosmetic — OCR is lossy in a way a native text
  layer isn't (a misread digit in a GSTIN or an EPCG duty-saved figure is a
  compliance-grade error), so OCR-sourced text probably needs weaker
  provenance than native text in the already-planned `extraction_audit`
  table, and maybe a lower bar before an OCR-sourced `Partial` escalates to
  the LLM tier. Not decided.
- **PaddleOCR needs a `Protocol`/adapter**, same idiom as `VirusScanPort`
  (`src/bronze/scan.py`) and the planned LLM tier — swappable, not a hard
  import — and it needs to be stubbed in CI, since `make ci` runs offline and
  PaddleOCR pulls model weights on first use.
- **All 50 current samples have native text layers, so none of them exercise
  the OCR path.** If OCR gets built now, it has to be validated against
  something — either synthetic scanned-image renders of these same PDFs
  (legitimate: we'd control the ground truth), or deferred until a real
  scanned document shows up. Not decided; flagged as the same "don't mock a
  layout you don't have ground truth for" principle applied one level deeper.

No adapter, parser, or migration was written. This is scoping only.
